# SHAPE Data Project Notes

These notes capture the project context that has been worked out in chat, so the repo remains understandable if the directory is moved or copied to a new location.

## Current Decision Points

- Treat SHAPE metadata as data, not as hand-authored portal HTML.
- Keep the reviewed registry as the human-maintained source of truth for curated descriptions and review status.
- Use generated artifacts for review, validation, and publishing, but do not treat generated artifacts as the canonical editing surface.
- Preserve the distinction between structural metadata and descriptive metadata:
  - database/observed metadata should win for structural facts such as years, geography levels, source systems, and last observed timestamps.
  - manual/reviewed metadata should win for descriptive fields such as display names, descriptions, domains, notes, caveats, confidence, and review status.
  - spreadsheet/imported metadata is a reference layer that fills gaps and helps reconcile source information, but it should not silently override deliberate manual review.
- Keep source IDs canonical. When the database, workbook, codebooks, or manual registry refer to the same source using different names, normalize those names rather than allowing duplicate source records.
- Prefer repeatable pipeline changes over one-off edits to generated files.

## The Two Portals

This repo has two web experiences that serve different purposes.

### Public Metadata Atlas

Location:

- Generated output: `site/`
- Generator code: `shape_metadata/publish.py`
- Data feeding the page: `site/metadata.json`, generated by the pipeline

Purpose:

- This is the public-facing SHAPE Metadata Atlas.
- It shows source domains, freshness, years, geographies, warnings, filters, cards, and table views.
- It is intended to be shared or archived as the final static web output.

Important implementation detail:

- `site/index.html`, `site/styles.css`, `site/app.js`, and `site/metadata.json` are generated files.
- If the atlas design, text, filters, card layout, table layout, CSS, or browser behavior needs to change, edit `shape_metadata/publish.py`, then rerun `./export.sh`.
- Direct edits under `site/` will be overwritten the next time the pipeline runs.

### Manual Registry Editor

Location:

- Entrypoint: `python3 -m shape_metadata.manual_editor --root .`
- Convenience script: `manual_editor.sh`
- Static editor assets: `shape_metadata/manual_editor_assets/`
- Backend/API code: `shape_metadata/manual_editor.py`
- Edited data file: `data/reviewed_registry.json`
- Local URL: `http://127.0.0.1:8765`

Purpose:

- This is the local editing portal for the reviewed registry.
- It loads reviewed records, observed database records, imported spreadsheet records, merged records, warnings, and load errors.
- It lets a reviewer update `data/reviewed_registry.json` while seeing database and spreadsheet context side-by-side.

Important implementation detail:

- The manual editor is not the same thing as the public atlas.
- The editor assets in `shape_metadata/manual_editor_assets/` are source files for the local editor, not generated `site/` output.
- If editor behavior or layout needs to change, edit `shape_metadata/manual_editor.py` for backend/API behavior or `shape_metadata/manual_editor_assets/` for the editor frontend.
- Saving in the editor writes back to `data/reviewed_registry.json`; it does not directly publish the atlas. Rerun `./export.sh` after registry edits to regenerate the public site and validation artifacts.

## Pipeline Flow

The normal export command is:

```bash
./export.sh
```

Equivalent direct command:

```bash
python3 -m shape_metadata --root .
```

The pipeline flow is:

1. Load local environment variables from `.env`, if present.
2. Load observed metadata from either:
   - `SHAPE_OBSERVED_SNAPSHOT`, or
   - the SHAPE SQL Server database when SQL credentials are configured.
3. Load imported reference metadata from either:
   - `SHAPE_IMPORTED_SNAPSHOT`, which may be JSON or XLSX,
   - Box when Box credentials are configured,
   - plus optional `SHAPE_CODEBOOK_SNAPSHOT`.
4. Load reviewed metadata from `data/reviewed_registry.json`.
5. Reconcile observed, imported, and reviewed records using the precedence rules in `shape_metadata/pipeline.py`.
6. Write review artifacts under `artifacts/`.
7. Generate the public atlas under `site/`.

## Data Layers

### Observed Metadata

Observed metadata represents what the live database or an observed snapshot says exists.

Configuration:

- `SHAPE_OBSERVED_SNAPSHOT=/path/to/file.json`
- or `SHAPE_MSSQL_USER` and `SHAPE_MSSQL_PASSWORD`

Current SQL defaults:

- host: `HCI-DB`
- database: `SHAPE`
- table: `adm.shapeDoc`
- expected source-level rows have schema populated while table and column are null

Observed metadata is intended to be strongest for structural facts. If the live database says a source has different years or geographies than the reviewed registry, the pipeline should surface that drift.

### Imported Reference Metadata

Imported metadata represents external reference material, currently from a workbook snapshot, Box, and optional codebook input.

Configuration:

- `SHAPE_IMPORTED_SNAPSHOT=/path/to/file.json`
- `SHAPE_IMPORTED_SNAPSHOT=/path/to/file.xlsx`
- `BOX_DEVELOPER_TOKEN` and `BOX_FILE_ID`
- optional `SHAPE_CODEBOOK_SNAPSHOT=/path/to/file.json`

The current workbook snapshot lives under:

- `data/inputs/Metrics captured by database_ACTIVE.xlsx`

Imported metadata helps fill gaps and identify mismatches, but reviewed registry decisions should remain explicit.

### Reviewed Registry

Reviewed metadata lives in:

- `data/reviewed_registry.json`

This is the human-curated layer. It should contain deliberate source descriptions, domains, notes, review status, confidence, review dates, caveats, and document references.

The manual editor saves this file after normalizing records and field order.

## Generated Artifacts

The pipeline writes:

- `artifacts/observed_metadata.json`: normalized observed/database layer.
- `artifacts/imported_metadata.json`: normalized imported/reference layer.
- `artifacts/reviewed_registry_draft.json`: reconciled merged registry that can be reviewed before accepting changes.
- `artifacts/validation_report.json`: machine-readable warnings.
- `artifacts/validation_report.html`: human-readable warnings.
- `site/`: static public atlas.

`artifacts/reviewed_registry_draft.json` is useful for review, but it should not automatically replace `data/reviewed_registry.json` without a human checking the changes.

## Validation And Warnings

Validation currently lives in `shape_metadata/pipeline.py`.

Existing warning categories include:

- missing reviewed registry entries for observed/imported sources.
- observed year drift between database and reviewed registry.
- domain mismatches between imported reference metadata and reviewed registry.
- stale codebook/source document references.
- non-contiguous available years.
- records that are not marked reviewed.

The validation report is generated at:

- `artifacts/validation_report.html`

## Local Environment And Portability

This directory is its own git repository. The `.git` directory is inside the project root, so moving the whole folder preserves git history, branches, remotes, and local repo metadata as long as hidden files are included.

Important local-only files:

- `.env`
- `.codex/`

Both are ignored by git. They move with the directory if the whole folder is moved or copied, but they will not be present after a fresh clone unless recreated.

Known external local dependency:

- `/opt/homebrew/lib/libmsodbcsql.18.dylib`

That path is the SQL Server ODBC driver path used by `.env` and as a fallback candidate in `shape_metadata/sources.py`. Moving this repo on the same Mac should not break that path. Moving to another machine may require installing the driver and updating `SHAPE_MSSQL_DRIVER`.

Other runtime expectations:

- `.codex/environments/environment.toml` currently refers to a conda environment named `shape-visualization`.
- Live database loading requires network and credential access to `HCI-DB`.
- Box loading requires Box credentials and the relevant file ID.

## GitHub CLI Auth Workaround

The GitHub CLI token may expire or become invalid in Codex sessions. When that happens, `gh auth status` reports something like:

```text
Failed to log in to github.com account dstone42
The token in default is invalid.
```

This was solved previously with GitHub's device-login flow:

```bash
gh auth login -h github.com --git-protocol ssh
```

Workflow:

1. Codex starts the command in an interactive terminal.
2. If `gh` prompts for the browser/device flow, Codex presses Enter to continue.
3. `gh` prints a one-time device code.
4. The user opens `https://github.com/login/device` in their normal browser, enters the code, and approves access.
5. Codex waits for the terminal session to finish, then verifies with:

   ```bash
   gh auth status
   ```

Expected successful state:

- logged in to `github.com` as `dstone42`.
- credential storage uses the keyring.
- git protocol is `ssh`.
- token scopes include `repo`.

After this succeeds, Codex can use `gh issue`, `gh repo`, `gh pr`, and related commands for this repository. Public read-only GitHub API calls may work without auth, but issue updates, closing issues, creating PRs, and other writes need a valid `gh` token.

## Common Workflows

### Edit Reviewed Metadata

1. Start the local editor:

   ```bash
   python3 -m shape_metadata.manual_editor --root .
   ```

2. Open `http://127.0.0.1:8765`.
3. Edit and save reviewed records.
4. Rerun:

   ```bash
   ./export.sh
   ```

5. Review `artifacts/validation_report.html` and `site/index.html`.

### Change The Public Atlas

1. Edit `shape_metadata/publish.py`.
2. Rerun `./export.sh`.
3. Review generated files under `site/`.
4. Do not make the final durable change directly in `site/`.

### Change Merge Or Validation Behavior

1. Edit `shape_metadata/pipeline.py`.
2. Add or update focused tests in `tests/test_pipeline.py`.
3. Run tests.
4. Rerun `./export.sh`.
5. Review `artifacts/reviewed_registry_draft.json` and `artifacts/validation_report.html`.

### Add Or Normalize Source Inputs

1. Edit `shape_metadata/sources.py`.
2. Update source aliases if the same source appears under multiple names.
3. Add tests that cover the real input shape.
4. Rerun `./export.sh`.

## Checks After Moving The Directory

After copying or moving the whole folder, run:

```bash
git status
git log --oneline -5
./export.sh
```

If the manual editor is needed, run:

```bash
python3 -m shape_metadata.manual_editor --root .
```

If database loading fails after the move, check `.env`, the ODBC driver path, SQL credentials, and access to `HCI-DB`.
